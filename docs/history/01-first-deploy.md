## 하려던 것

Day 2 에 글자로 대화하는 화면과 서버 함수를 만들고, Day 3 에 Vercel 에 연결해 폰에서 열어본다.
진짜 목표는 챗봇이 아니라 **고치면 폰에 반영되는 길을 뚫는 것.**

## 실제로 한 것

- `public/index.html` — 대화 화면 한 장. 입력창, 대화 기록, 오류 표시
- `api/chat.js` — API 키를 숨긴 채 Gemini 로 전달하는 서버 함수
- `.gitignore`
- Vercel 에 저장소 연결, 환경변수 `GEMINI_API_KEY` 설정, 배포

**의존성을 하나도 쓰지 않았다.** 초보자 프로젝트에서 배포가 실패하는 가장 흔한 원인이 "설치 실패" 인데, 설치할 것이 없으면 그 이유로는 실패할 수 없다.

**오류를 화면에 그대로 띄우게 만들었다.** 보통은 감추지만, 원인이 보여야 고칠 수 있다. 이 선택이 바로 그날 값을 했다.

## 막혔던 것

**모델이 폐기되어 있었다.**

- **증상** — 첫 호출에서 빨간 상자.

  > Gemini 오류 — This model models/gemini-2.5-flash is no longer available to new users. Please update your code to use models/gemini-3.6-flash for the latest features and improvements. We recommend you to use the Interactions API.

- **원인** — 계획을 세울 때 정한 `gemini-2.5-flash` 가 그 사이에 신규 사용자에게 제공 중단되었다. 클로드의 지식이 2026-05 까지라 그 이후 변경을 알 수 없었다.
- **해결** — 모델 이름을 `gemini-3.6-flash` 로 교체. 검색으로 이 모델이 기존 방식(`generateContent`)에서 그대로 쓰인다는 것을 확인한 뒤 바꿨다. 추측으로 바꾸지 않았다.
  덧붙여 **`GEMINI_MODEL` 환경변수로도 바꿀 수 있게** 했다. 다음에 또 바뀌면 코드 수정 없이 Vercel 설정만 고치면 된다.
  오류 메시지에 **사용한 모델 이름이 함께 찍히도록** 했다.

**이 오류가 오히려 좋은 소식이기도 했다.** "키가 틀렸다" 가 아니라 "모델이 없다" 였다는 것은, **키 인증은 이미 통과했다**는 뜻이다. 환경변수 설정이 정상임이 같이 확인됐다.

## 계획과 달랐던 점

Day 3 은 원래 사용자만의 작업이었는데, 모델 폐기 오류 때문에 클로드의 수정이 중간에 한 번 끼어들었다. 계획서의 Day 3 항목에 그 줄을 추가했다.

## 바뀐 결정

- `decisions.md` — **대화 모델을 Gemini 3.6 Flash 로.** 모델 이름은 생각보다 자주 바뀐다는 것을 배웠으므로 환경변수로 교체 가능하게 만듦
- **API 방식은 바꾸지 않았다.** 구글이 새 방식(Interactions API)을 함께 권했지만 기존 방식도 계속 지원된다. 고장 하나를 고치는 데 구조를 갈아엎지 않는다. 단 **Day 4 에서 한 번 검토한다** — 그 방식은 대화 기록을 서버가 대신 들고 있어 주므로, Day 4 의 "문맥 잇기" 를 더 간단하게 만들 수도 있다

## 배운 것

**계획은 틀린다. 중요한 건 틀린 걸 빨리 알아채는 구조다.**
모델 이름을 확신을 갖고 정했는데 폐기돼 있었다. 그런데 오류를 화면에 그대로 띄워둔 덕분에 구글이 "이 모델 대신 저 모델을 써라" 까지 알려준 문장을 그대로 읽을 수 있었고, 원인 파악에서 수정까지 5 분이 걸렸다.
"문제가 발생했습니다" 로 감췄더라면 키·배포·코드를 하나씩 뒤졌을 것이다.

**이것이 C(점검)를 구체적으로 만들어야 하는 이유다.** "안 된다" 가 아니라 **"무엇이 어떻게 안 되는지"** 가 보여야 고칠 수 있다.

**Vercel 환경변수의 함정** — 값을 추가하는 것만으로는 이미 돌아가는 배포에 적용되지 않는다. Redeploy 가 필요하다. (이번에는 코드 푸시가 재배포를 겸해서 걸리지 않았다.)
