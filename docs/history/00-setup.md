## 하려던 것

코드를 쓰기 전에 **무엇을 어떻게 만들지부터 정하기.** 다른 AI 가 준 초안을 그대로 실행하려다 멈추고, 그 초안이 이 상황에 맞는지부터 검토했다.

## 실제로 된 것

**초안 검토** — 받아온 설계의 뼈대(음성 인식 → 대화 → 음성 합성 → 아바타)는 옳았지만, 실제로 돌리면 안 되는 부분이 있었다.

- 아바타 영상 주소가 자리표시자 문자열이라 아무것도 안 나옴
- 화면 쪽에 오디오 재생 코드가 없어 소리가 안 남
- 대화 기록을 안 보내서 매번 첫 문장처럼 처리됨 — 상황극이 3턴이면 무너짐
- `127.0.0.1` 전제라 폰에서 열리지 않음

**제약 확정** — 폰(안드로이드)과 아이패드만 사용. 데스크톱 없음. 터미널 못 씀. 그래서 로컬 서버가 아니라 **깃허브 푸시 → 자동 배포** 구조로 방향을 틀었다.

**문서 네 개 작성** — `CLAUDE.md`(행동 지침), `docs/overview.md`(밑그림), `docs/plan.md`(Day 1~16 할 일), `docs/decisions.md`(결정 기록 7건).

**자동화 세 가지**

- `.claude/hooks/session-start.sh` — 세션이 열릴 때마다 현재 상태와 오늘 할 일을 자동으로 읽어옴
- `/today` — 오늘의 할 일 불러오기
- `/milestone` — 작업 덩어리가 끝날 때 이 폴더에 기록 남기기

## 막혔던 것

**아이패드 브라우저.** 처음에는 "아이패드는 사파리가 불안정하니 크롬을 쓰면 되겠지" 로 계획을 세웠는데, 사용자가 실제로 크롬을 쓴다고 알려주면서 다시 확인해야 했다.

- **증상** — 아이패드 크롬에서는 음성 인식 기능이 목록에 있는 것처럼 보이면서 실제로는 동작하지 않는다. 오류도 안 난다
- **원인** — 애플 정책상 아이패드의 모든 브라우저는 WebKit 으로 돈다. 그런데 앱 안의 웹뷰에서는 이 기능이 노출만 되고 작동하지 않는다 (WebKit Bug 239816)
- **어떻게 풀었나** — 아이패드는 **사파리로만** 지원하기로 하고, 기능이 있는지 묻는 대신 **몇 초간 반응이 오는지**로 판단해 타이핑 안내로 넘기는 먹통 감지를 넣기로 했다

**공식 문서 접근 차단.** 구글과 버셀 공식 문서가 작업 환경의 네트워크 정책에 막혀 무료 한도 수치를 확정하지 못했다. 검색으로 본 값은 있었으나 자주 바뀌는 값이라 **문서에 적지 않고 "가입 화면에서 확인"** 으로 남겼다.

## 계획과 달랐던 점

계획서를 **주차 단위로 먼저 썼다가 하루 단위로 다시 썼다.** 주 단위는 열 때마다 "이번 주에 뭘 하지" 를 다시 판단해야 해서, 처음 하는 사람에게는 판단할 거리가 너무 많았다.

## 바뀐 결정

`decisions.md` 에 7건 기록. 핵심은 셋.

- 립싱크 영상 대신 **브라우저가 실시간으로 그리는 아바타** — 영상은 한 마디에 10~60초라 대화가 성립하지 않음
- 허깅페이스 대신 **Vercel** — 푸시하면 자동 배포되는 루프가 폰 개발의 전부인데, GPU 가 필요 없어지면서 허깅페이스의 장점이 사라짐
- **빠른 길과 이해되는 길이 갈리면 후자로 간다** — 사용자의 동기에 "만들어보는 경험 자체" 가 포함되어 있음이 확인됨
